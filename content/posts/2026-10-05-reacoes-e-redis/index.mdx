Este é o quinto post da série **Manual do Blog**. Ele explica a única parte do blog que grava dados de visitantes em um banco próprio: as reações dos posts, que usam Redis (Upstash). As variáveis necessárias estão em [Variáveis de ambiente e deploy](/blog/variaveis-de-ambiente-e-deploy).

---

## Visão geral

Cada post tem três reações, definidas em `lib/reactions/config.ts`:

| Tipo      | Emoji | Rótulo  |
| --------- | :---: | ------- |
| `like`    |  ❤️   | Gostei  |
| `learned` |  💡   | Aprendi |
| `thanks`  |  ☕   | Valeu!  |

Cada visitante tem **no máximo uma reação por post**: clicar em outra reação troca a escolha, e clicar de novo na reação escolhida a remove.

As peças envolvidas:

- **`lib/reactions/config.ts`**: tipos, rótulos e a função que valida um tipo.
- **`lib/reactions/store.ts`**: leitura e escrita no Redis.
- **`lib/reactions/visitor.ts`**: o cookie que identifica o visitante.
- **`lib/reactions/rate-limit.ts`**: os limites de requisições.
- **`lib/redis.ts`**: cliente do Upstash, configurado pelas variáveis de ambiente, e o prefixo de ambiente das chaves.
- **`app/api/reactions/[slug]/route.ts`**: rota com `GET`, `PUT` e `DELETE`.
- **`components/post-reactions.tsx`**: componente de cliente que exibe e envia as reações.
- **`app/api/keepalive/route.ts`**: rota chamada pelo cron para manter o banco ativo.

## Como o visitante é identificado

O blog não pede login, e a identidade de quem reage é um cookie chamado `visitor_id`, com um UUID gerado no servidor. Ele:

- só é criado na **primeira reação**: ler as contagens de um post nunca grava cookie;
- é `httpOnly` (o JavaScript da página não consegue lê-lo), `sameSite=lax` e, em produção, `secure`;
- vale por 1 ano;
- é validado a cada requisição, porque vem do navegador: um valor que não seja um UUID v4 é tratado como se não existisse.

O cookie e os dados guardados estão descritos na [política de privacidade](/privacy).

## Dados no Redis

Cada post usa dois hashes. As chaves das reações e do limite de requisições levam o prefixo do ambiente (veja [Ambientes separados no Redis](/blog/variaveis-de-ambiente-e-deploy#ambientes-separados-no-redis)); a do keepalive, não:

| Chave                                   | Conteúdo                                                      |
| --------------------------------------- | ------------------------------------------------------------- |
| `production:reactions:meu-post:counts`  | Contagem de cada tipo de reação                               |
| `production:reactions:meu-post:choices` | ID do visitante (o do cookie) e o tipo que ele escolheu       |
| `production:rate-limit:...`             | Janelas do limite de requisições, indexadas por um hash do IP |
| `keepalive:last_run`                    | Data da última execução do keepalive, sem prefixo de ambiente |

O hash `choices` é a fonte da verdade, e o `counts` é derivado dele e pode ser reconstruído. Nenhum dos dois expira.

Trocar ou remover uma reação depende da escolha anterior do visitante, e uma transação simples do Redis não consegue decidir com base nesse valor. Por isso a escrita é feita por um **script Lua** que roda de forma atômica no Redis:

<Steps>
  <Step title='Lê a escolha anterior'>
    Busca no hash `choices` o que aquele visitante tinha escolhido antes, se algo.
  </Step>

<Step title='Ajusta os contadores'>
  Se a escolha mudou, diminui o contador do tipo anterior e aumenta o do novo.
  Ao remover, só diminui.
</Step>

<Step title='Atualiza a escolha'>
  Grava o novo tipo em `choices`, ou apaga a entrada do visitante quando a
  reação é removida.
</Step>

  <Step title='Devolve as contagens'>
    Responde com o hash `counts` atualizado, que o servidor devolve para a página.
  </Step>
</Steps>

Como o script verifica a escolha anterior antes de mexer nos contadores, repetir a mesma requisição não conta duas vezes. Dois cliques simultâneos também não corrompem os números, porque o Redis executa o script inteiro de uma vez.

<Callout variant='info' title='Removendo um tipo de reação'>
  Dados de um tipo que saiu da configuração continuam no Redis, mas são
  ignorados: o contador não aparece e a escolha daquele visitante conta como
  nenhuma.
</Callout>

## Limite de requisições

Para dificultar abusos, as escritas passam por dois limites, ambos por IP, usando `@upstash/ratelimit` com janela deslizante:

| Limite           | Valor         | Para que serve                                                    |
| ---------------- | ------------- | ----------------------------------------------------------------- |
| Escritas         | 20 por minuto | Frear quem envia reações em sequência                             |
| Novos visitantes | 10 por hora   | Impedir que um script ganhe uma identidade nova a cada requisição |

O segundo limite existe porque, sem cookie, cada escrita criaria um visitante novo, e limitar só a frequência não impediria de inflar as contagens.

O IP vem do primeiro valor do cabeçalho `x-forwarded-for` ou, na falta dele, de `x-real-ip`. Sem nenhum dos dois, todas as requisições são tratadas como o mesmo IP, `unknown`. O endereço **nunca é gravado**: o que chega ao Redis é um hash HMAC-SHA256 do IP, calculado com o `RATE_LIMIT_SECRET`.

Se o Redis falhar durante a checagem do limite, a requisição segue (o limite "falha aberto"). Isso não deixa a escrita passar de fato, porque a gravação que vem depois falharia pelo mesmo motivo.

## A API

Todas as rotas ficam em `/api/reactions/slug-do-post` e respondem com o estado atual do post, sem cache, porque a resposta mistura as contagens públicas com a escolha privada do visitante:

```json
{
  "counts": { "like": 12, "learned": 3, "thanks": 0 },
  "choice": "learned"
}
```

O campo `choice` é `null` para quem ainda não reagiu. Erros têm o formato `{ "error": "codigo" }`.

### GET

Devolve as contagens e, se o cookie existir, a escolha do visitante. Funciona também em posts arquivados.

### PUT

Recebe o tipo da reação no corpo da requisição e cria ou troca a escolha do visitante:

```json
{ "type": "thanks" }
```

<Steps>
  <Step title='Confere o post'>
    Se o post não existe (ou é rascunho), responde `404`. Se está arquivado, responde `409`.
  </Step>

<Step title='Confere o limite de escritas'>
  Se o IP passou de 20 escritas por minuto, responde `429`.
</Step>

<Step title='Valida o tipo'>
  Se o tipo não for um dos três da configuração, responde `400`.
</Step>

<Step title='Identifica o visitante'>
  Usa o cookie, se houver. Sem cookie, confere o limite de novos visitantes
  (`429` se estourou) e cria o cookie.
</Step>

  <Step title='Grava e responde'>
    Aplica o script Lua e devolve o estado atualizado.
  </Step>
</Steps>

### DELETE

Remove a escolha do visitante, depois das mesmas conferências de post e de limite do `PUT`. Sem cookie não há nada para remover, então a rota só devolve o estado atual e **não cria cookie**.

### Códigos de erro

| Status | `error`                 | Quando                                              |
| :----: | ----------------------- | --------------------------------------------------- |
|  400   | `invalid-reaction-type` | O corpo do `PUT` não traz um tipo válido            |
|  404   | `post-not-found`        | O post não existe ou é rascunho                     |
|  409   | `post-archived`         | Tentativa de escrever em um post arquivado          |
|  429   | `rate-limited`          | Limite de escritas ou de novos visitantes estourado |
|  503   | `store-unavailable`     | O Redis falhou ao ler ou gravar                     |

Sem o `RATE_LIMIT_SECRET`, o `PUT` e o `DELETE` respondem `500`, porque não conseguem calcular o hash do IP.

## O componente

O `PostReactions` recebe o `slug` do post (e `readOnly`, para posts arquivados) e funciona assim:

- Ao montar, faz um `GET` para carregar as contagens e a escolha do visitante. Se falhar, mostra um traço no lugar dos números.
- Contagem zero, ou ainda em carregamento, não mostra número, para um post novo não aparecer com "0 0 0".
- Ao clicar, **atualiza a tela na hora** (atualização otimista) e só então envia a requisição: `PUT` para escolher ou trocar, `DELETE` ao clicar na reação já escolhida.
- Se a requisição falhar, a tela volta sozinha ao estado anterior e aparece uma mensagem: uma específica para o limite de requisições e uma genérica para os outros erros.
- Cliques enquanto uma requisição está em andamento são ignorados. Os botões não ficam desabilitados nesse intervalo.
- Cliques também são ignorados enquanto as contagens não carregaram, ou se o carregamento falhou. Nesse período os botões recebem `aria-disabled`.
- Em posts arquivados, os botões ficam desabilitados e só mostram as contagens.

A escolha do visitante vem do servidor, então ela continua marcada ao recarregar a página ou voltar ao post depois.

Sobre o layout e a acessibilidade:

- em telas pequenas, o rótulo ("Gostei", "Aprendi", "Valeu!") aparece ao lado do emoji; a partir do breakpoint `md`, ele vira um tooltip;
- cada botão informa se está selecionado (`aria-pressed`) e a contagem no `aria-label`;
- as mensagens de erro ficam em uma área de status sempre presente na página, para os leitores de tela as anunciarem quando aparecem.

<Callout variant='tip' title='Testando localmente'>
  Em desenvolvimento, as chaves levam o prefixo `local` e não afetam a produção.
  Para reagir como um visitante novo, apague o cookie `visitor_id` no navegador.
  Como em desenvolvimento todas as requisições partem do mesmo IP, elas dividem
  o limite de 10 novos visitantes por hora. Se chegar ao limite, apague no
  painel do Upstash as chaves que começam com `local:rate-limit:`.
</Callout>

## Adicionando um tipo de reação

Edite `lib/reactions/config.ts`: acrescente o tipo em `REACTION_TYPES` e a configuração correspondente em `REACTION_CONFIG`.

```ts title="lib/reactions/config.ts"
export const REACTION_TYPES = ['like', 'learned', 'thanks', 'clap'] as const;

export const REACTION_CONFIG = {
  like: { emoji: '❤️', label: 'Gostei' },
  learned: { emoji: '💡', label: 'Aprendi' },
  thanks: { emoji: '☕', label: 'Valeu!' },
  clap: { emoji: '👏', label: 'Parabéns' },
} as const satisfies Record<ReactionType, { emoji: string; label: string }>;
```

O TypeScript acusa um erro se o tipo existir em uma lista e faltar na outra, e a API, o armazenamento e o componente passam a usar o novo tipo automaticamente.

## Keepalive do Redis

Bancos gratuitos de serviços como o Upstash podem ser pausados ou arquivados quando ficam sem uso. Para evitar isso, o projeto tem uma rota que escreve no Redis periodicamente, chamada por um cron da Vercel.

O agendamento fica no `vercel.json`:

```json title="vercel.json"
{
  "crons": [
    {
      "path": "/api/keepalive",
      "schedule": "0 12 * * 1,4"
    }
  ]
}
```

Isso significa **segundas e quintas, às 12:00 UTC**. Os crons da Vercel só rodam em deploys de produção.

A rota `/api/keepalive`:

- Exige o cabeçalho `Authorization: Bearer` com o valor de `CRON_SECRET`. Sem a variável configurada, **nenhuma** requisição é autorizada (a rota "falha fechada" e responde `401`).
- Grava a data atual na chave `keepalive:last_run`, lê o valor de volta e o devolve, provando que a escrita foi persistida.
- Em caso de erro, responde `500` com uma mensagem genérica; os detalhes ficam apenas nos logs.
- Desativa o cache, para que cada chamada realmente alcance o Redis.

Para testar manualmente em produção:

```bash
curl -H "Authorization: Bearer $CRON_SECRET" https://seu-dominio.com/api/keepalive
```

A resposta esperada é um JSON com a chave e a data gravada:

```json
{ "key": "keepalive:last_run", "value": "2026-10-26T12:00:00.000Z" }
```

## Limitações conhecidas

<Callout variant='warning' title='Não é à prova de abuso'>
  A identidade do visitante é um cookie, então quem limpa os cookies ou usa uma
  janela anônima pode reagir de novo; o limite de novos visitantes por IP reduz
  esse efeito, mas não o elimina. Pessoas atrás do mesmo IP (empresa, rede
  móvel) compartilham os limites, e quem troca de IP tem limites novos. Fora da
  Vercel, o cabeçalho `x-forwarded-for` pode ser forjado pelo cliente, o que
  enfraquece o limite. E, se o Redis falhar durante a checagem, o limite é
  ignorado.
</Callout>

O que está protegido: a API só aceita `slug` de posts que existem, e a escrita é atômica, então requisições simultâneas não passam do limite de uma reação por visitante.

Para um blog pessoal, esse nível de proteção costuma ser suficiente. Se virar um problema, os caminhos naturais são exigir algum tipo de verificação para novos visitantes ou autenticar quem reage.
